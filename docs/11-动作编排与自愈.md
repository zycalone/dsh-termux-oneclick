# 11 · 动作编排与自愈（把点手机做稳）

> 这一篇是**借鉴成熟项目后补上的能力**，不是原创概念。思路来源见文末。

## 为什么需要这个

用 `tap-text` 直接点，会撞上三种失败：

| 失败模式 | 表现 | 后果 |
|---|---|---|
| **瞎点** | 文字刚点过，界面还没刷新就点下一处 | 点穿到别的页面，越操作越乱 |
| **赌时间** | 用 `sleep 3` 等页面加载 | 慢了白等，快了乱点 |
| **烧 token** | 每次读屏都吐全量控件树 | 一屏几十行，几轮就撑爆上下文 |

Android 上这三个坑尤其致命，因为**控件树拿不到的东西你完全看不见**（微信就是空的），一次点穿后面全是连锁错误。

---

## 一、读屏瘦身：`text --click`

```bash
appctl text --click        # 只给可点元素（默认推荐）
appctl text --json         # 结构化，方便一次规划多步
appctl text --max 40       # 限制条数
appctl text --scroll       # 只看可滚动容器（找列表）
```

实测对比（B 站视频页，同一时刻）：

```
appctl text           → 23 行
appctl text --click   → 16 行      # 少 30%，且全是能点的
```

去重规则：同一文字 + 同一位置（按 8px 网格）只留一条，因为 Android 常把父容器的 text 复制给子节点。

`--json` 每条长这样，模型可以照着直接算：

```json
{"text": "点赞", "class": "Button", "cx": 1327, "cy": 1571,
 "bounds": [1191,1511,1463,1631], "clickable": true,
 "scrollable": false, "pkg": "tv.danmaku.bili"}
```

---

## 二、点完自我复核：`tap-text "文字" --verify`

```bash
appctl tap-text "关注" --verify          # 点完比对界面指纹，没变化就重试
appctl tap-text "关注" --verify --tries 5
```

实现：点之前把 `text --click` 的输出算一个指纹（md5 前 8 位），点完等 1.2s 再算一次。

```
tapped [关注] at 769,2646 changed=yes          # 有变化，成功返回 0
tapped [关注] at 769,2646 changed=no (第 1/3 次，界面没变化，重试)
GIVE_UP: 关注（试了 3 次，界面始终没变化；先 text --click 看看现在到底有什么）   # 返回 4
```

**这是最省心的一个开关**：失败的点击会被自己发现并重试，而不是把错误界面留给模型去猜。

---

## 三、等元素出现：`wait-text "文字" 15`

```bash
appctl wait-text "通讯录" 15
# FOUND: 通讯录（等了 2s）        → 0
# TIMEOUT: 通讯录（15s 内没出现）  → 3
```

比 `sleep 3` 好在：**用条件等，不用时间赌**。慢的机器不多等，快的机器不空转。

---

## 四、控件知识库：`appctl kb`

把摸清过的界面存下来，下次直接查，不用再 dump：

```bash
appctl kb save 微信首页      # 存当前界面（文件名可省，自动用包名）
appctl kb get 微信首页       # 读回来
appctl kb list              # 有哪些
```

存下来的文件长这样（`~/dsh-phone/kb/微信首页.txt`）：

```
# pkg: com.tencent.mm
# saved: 2026-11-13 00:08
[可点] 通讯录 <TextView> @180,2100
...
```

**价值在跨天复用**：同一套界面上次摸过，这次直接读文件，省掉重新探索的 token 和时间。
（AppAgent 的"探索阶段建元素知识库"就是这个思路。）

---

## 五、多步一次下发：`act_batch.py`

模型一次输出整串动作，本地顺序执行：

```bash
python ~/dsh-phone/act_batch.py steps.json              # 真跑
python ~/dsh-phone/act_batch.py steps.json --dry-run    # 只打印，不碰屏幕
python ~/dsh-phone/act_batch.py steps.json --keep-going # 失败也继续
```

`steps.json`：

```json
[
  {"act": "open",      "pkg": "com.tencent.mm"},
  {"act": "wait-text", "text": "通讯录", "timeout": 15},
  {"act": "tap-text",  "text": "通讯录", "verify": true},
  {"act": "sleep",     "seconds": 1},
  {"act": "text",      "opts": ["--click"]},
  {"act": "shot"}
]
```

干跑输出（实测）：

```
[1] DRY  appctl cur
[2] DRY  appctl text --click
[3] DRY  appctl wait-text '返回' 3
[4] DRY  appctl tap-text '返回' --verify
[5] sleep 0.2s
[6] DRY  appctl shot
完成 6/6 步
```

**默认遇错就停**（避免错误连锁），需要它硬着头皮跑完再加 `--keep-going`。

支持的动作：`cur` `text` `open` `tap` `tap-text` `type` `key` `swipe` `wait-text` `kb-save` `kb-get` `sleep` `shot` `apps`。

## 六、一句推荐流程

```bash
appctl cur                              # 在哪个 App
appctl text --click                     # 能点什么
appctl tap-text "目标" --verify          # 点，并自检
appctl shot                             # 截图给视觉模型复核（关键步骤才用）
```

前 3 步零 token（纯命令行），第 4 步才把图交给模型 —— **视觉是贵的，别拿它当眼睛用，拿它当复核用**。

## 实测与局限（照实写）

**实测通过**（2026-11-13，真机）：

- `bash -n appctl.sh` / `act_batch.py` / `ui_text.py` 语法检查 ✅
- `text --click` 16 行 / `text` 23 行，去重生效 ✅
- `text --json` 输出结构正确 ✅
- `kb save / list / get` 往返正常，头部记录 pkg 与时间 ✅
- `batch --dry-run` 6 步全部正确解析（含 `sleep`）✅
- `wait-text` 命中返回 `FOUND`、未命中返回 `TIMEOUT` ✅

**局限**：

- `--verify` 判断的是"界面指纹有没有变"，**不是"点对了没有"**。有些操作界面不变（比如勾选一个复选框之外的静默提交），会被判成失败重试 —— 这类场景别加 `--verify`。
- 控件树是空的 App（**微信就是**）→ `wait-text` / `kb save` 全部拿不到东西，这套办法对它无效。
- 没有实现真正的"反思"（让模型看截图说自己错在哪）。现在的自愈是**机械重试**，够用，但不聪明。
